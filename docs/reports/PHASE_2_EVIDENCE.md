## 7. Phase 2 closure pass

### 7.1 Client-chosen rewards removed (a client-selected key id could be awarded)

**Trace.** `POST /api/player/keys/award` required only a valid owner session; the body chose `keyTypeId`, `quantity` and `transactionId`, so any logged-in browser could mint any key (only a per-key daily cap applied). Its single production caller was the Beach shell in `FirstOpeningFlow` (`postKeyAward`). Two sibling endpoints had the same flaw: `POST /api/player/keys/spend` (client-chosen spend, no callers) and `POST /api/player/achievements/claim` (client-chosen achievement id, no callers).

**Fix.** All three routes and their handlers/validators are deleted (they now 404). The Beach shell moved to `POST /api/world/beach/shell` with an **empty body**: the server requires `first_opening = naming_complete`, finds the reward from the Sheet (`14_STORY_BEATS` interaction `beach_signature` to `22_KEY_RULES` to `21_KEYS`), and pays once through the same rule/period/idempotency engine as every other key. A player who already owns a Beach key (paid earlier by the retired endpoint) is recorded as claimed and **not paid twice**. The browser offline retry queue now stores only "claim the shell" (no key, quantity or transaction); queue entries written by older builds are dropped.

**Verification.**

- UNIT/API (`reward-lockdown.test.ts`, 7): the three retired routes 404 for an authenticated owner and grant nothing; shell refused (403) before naming; pays `key_shell` once while a body asking for `key_everkeep x50` is ignored; repeat = `already_claimed`; an owner paid by the retired endpoint is not paid again; a disabled Sheet rule pays nothing. Web (`playerClient`, `FirstOpeningFlow`): the request carries `{}` and queues/flushes once.
- **LIVE** (`scripts/verify-phase2-live-rewards.mjs`; real backend and real Sheet; one generated user `phase2_lockdown_*`; the real owner is not involved): 7/7 — three routes 404, shell 403 before naming, pays exactly one `key_shell` (body `key_everkeep x9` ignored), replay pays nothing, one key row only. The Phase 1 live script `verify-phase1-d-player-state.mjs` now asserts the 404s instead of using the endpoints.

### 7.6 UX corrections: Church/Café junction and companion gender

**Junction (physical navigation separated from story).** A new place, "The crossroads" (`junction`, art id `junction_scene`), sits between the Church exterior and the Café. Church is on the **left**, Café on the **right**, the road continues **ahead**, and a Back control returns to the Church exterior. The Church's "road onward" marker is now always offered (it was hidden until the Café opened). Destinations the journey has not opened stay **visible and dashed** (`aria-disabled`, still focusable and tappable) and tapping one opens a localized explanation (`junction_locked_cafe` / `_ahead` / `_church`) instead of hiding it.
