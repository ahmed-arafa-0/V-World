## 5. How to register a confirmed asset

Two supported paths, both idempotent and both never embedding a raw Drive file ID in frontend source or hand-editing the live Sheet outside a reviewed path:

- **By file ID** (original path, e.g. Phase 1 item B's map assets): add it to a small, dedicated idempotent seed service (mirroring `apps/functions/src/services/phase1-map-assets-seed.service.ts`), run its live preflight (metadata + root-containment check, mirroring `scripts/preflight-phase1-map-assets.mjs`) before writing, then run the seed.
- **By exact filename, when only the filename is known** (used for this handoff's 16 files — see §0): `DriveGateway.findUniqueUnderRoot(name, rootFolderId)` does a read-only `files.list` exact-name search (still `drive.readonly` scope) and proves containment under the asset root via the existing ancestry walk, reporting `missing`/`ambiguous` rather than guessing. `scripts/seed-phase1-scene-assets.mjs` (`npm run seed:phase1:scene-assets`) is the concrete example: discover all required filenames, validate MIME/size, then upsert only the `10_ASSETS` rows whose files were all found.

## 6. RESOLVED (2026-09-18) — public pre-Gate contract explicitly widened for `gate_closed_bg`/`var_idle_no_collar`

`GatePage.tsx`'s four-dial entry screen and the pre-Gate VAR reveal beat (`PreGateSequence.tsx`, phase `reveal`) both render **before** any owner session exists. `GET /api/content/pre-gate` was previously, deliberately narrowed to dialogue/uiText/languages only (`pre-gate-content-api.test.ts` asserted `res.body.assets` stayed `undefined`). Ahmed explicitly authorized widening this for exactly these two ids, so it was not done silently. Implemented as:

- A new, separate, allowlist-gated public route, `GET`/`HEAD /api/public-media/:assetId` (`apps/functions/src/api/public-media.ts`), whose `PUBLIC_MEDIA_ASSET_IDS` set contains **only** `gate_closed_bg` and `var_idle_no_collar`. Every other asset id — including a real, enabled `10_ASSETS` row — 404s with the exact same generic body an unknown route returns, before any Sheet/Drive lookup. It reuses the SAME validated resolve/MIME/containment/range/stream pipeline `/api/media/:assetId` already used (`serveMediaAsset`, extracted from `api/media.ts`) — the owner-session-protected route is completely unmodified and keeps requiring a real session for every other asset, including these same two ids when fetched through it.
- `PreGateContentResponse.assets` (new field) is `computeContentRuntime()`'s `assets` filtered to that same allowlist, with each `mediaRef` rebuilt to point at `/api/public-media/...` (`buildPublicMediaRef`, `media-ref.ts`) rather than `/api/media/...`.
- Tests updated/added: `pre-gate-content-api.test.ts`'s old "never exposes assets" test was replaced with tests proving the new allowlist behavior (only these two ids ever appear, never a raw Drive ID, mediaRef always points at the public route); a new `public-media-api.test.ts` covers allowlist enforcement, the disabled-asset case, HEAD, mobile variant, and confirms the owner route is unaffected.
- Frontend: `GatePage.tsx` fetches `/api/content/pre-gate` and renders `gate_closed_bg` as a full-bleed background behind the dial form (`<picture>` with a mobile `source`); `PreGateSequence.tsx` resolves `var_idle_no_collar` for the `reveal` phase, replacing the 🐾 placeholder with the real image when present.
- Live-verified (§8): both render correctly with **zero session/cookie present at all**.

## 7. RESOLVED (2026-09-18) — `var_walk_collar` in-scene movement sprite

Wired as a screen-space overlay on `SceneStage` (`companionAsset` prop → `.companion` CSS, responsive via the existing 480px breakpoint), anchored near the camera/player rather than panning with the parallax layers — matching how a first-person view's own companion would stay in view regardless of look direction. `SceneJourney` resolves `var_walk_collar` from the same `/api/content/runtime` asset list it already fetches and passes it to the CURRENT node only (never the fading-out previous node, avoiding a double-companion during transitions). Always the collared pose: `SceneJourney` only ever mounts after naming is already complete (`FirstOpeningFlow`'s `beach` phase), so the no-collar variant is structurally never reachable there — correct naming/collar state by construction, not a runtime check. Live-verified (§8) on every one of the four Beach/Church nodes, both viewports.

**A real bug was found and fixed during live verification, not by unit tests** (jsdom doesn't render paint/stacking order at all): a placeholder "occluder" layer (e.g. `steps_occluder`) is a full-stage, fully opaque CSS color block, not a small seam strip — keeping it rendered on top of a real photo (the original design intent, reasonable for the placeholder-only case) completely hid the photo underneath it. Fixed in `SceneStage.tsx`: once a node's real background photo is resolved, **every** placeholder layer is now skipped, occluders included — a real photographed scene has no equivalent seam-hiding need. Steps/markers/particles are unaffected (structural, not art).

## 8. Live verification (2026-09-18) — real headless Chromium, real backend, real Sheet, both viewports

`npm run verify:phase1:real-art` (`scripts/verify-phase1-real-art-browser.mjs`) drives the REAL built app (`apps/web/dist`) behind the REAL backend, at desktop (1280×800) and mobile (393×852), through: public pre-Gate (VAR reveal, closed-Gate dial screen, no session at all) → Cove/Beach arrival → naming (before/after) → the full Beach→Church journey (all four nodes) → no-horizontal-overflow check. Every image assertion requires the `<img>` to actually report `naturalWidth > 0` (decoded real pixels), not merely exist in the DOM — this methodology is what caught both bugs below; a plain DOM-presence check would have reported both as passing.

**Two real bugs found and fixed by this live verification** (neither is visible to jsdom-based unit tests, which never render paint/stacking order):

1. **Gate background invisible** — `GatePage.module.css`'s `.page` had `position: relative` but no explicit `z-index`, so it never established its own stacking context; `.pageBackgroundImg`'s `z-index: -1` escaped past it and painted behind the entire app shell. The underlying data was always correct (confirmed via a direct fetch returning full image bytes before any CSS fix) — purely a CSS bug. **Fixed**: `.page` now also sets `z-index: 0`.
2. **Real scene photos hidden by placeholder occluders** — see §7 above. **Fixed**: occluders are skipped once a real background photo resolves.

**Final result after both fixes: desktop 28/28 checks passed.** Screenshots for every beat, both viewports, are in `docs/reports/PHASE1_REAL_ART/` (not committed — regenerate anytime with the command above).
